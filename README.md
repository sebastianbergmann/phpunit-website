# phpunit.de

This is the repository for the website that is hosted at `https://phpunit.de/`.

The website consists of static files in `public/`. The eleven top-level pages (`public/*.html`) are generated by a small PHP program from the templates in `templates/` and the configuration in `config.php`. Everything else in `public/` is maintained by hand.

## The build is run by hand

Nothing runs the generator automatically: there is no cron job, no CI pipeline, and no hook that does it.

I run it manually, review the changes it made in `public/`, commit them, and then push `public/` to the web server:

```
./bin/build.php
git diff public/
```

This matters because the generator is date-aware (see [What is derived](#what-is-derived)). A version that is configured with a release date in the future does not appear as released on the website on that day by itself. It appears when the build is run on or after that day and the result is pushed.

Only `public/` exists on the web server. See [SECURITY.md](SECURITY.md).

## Setup

PHP 8.5 is required.

```
./tools/composer install
```

This installs PHPUnit for the tests and generates the autoloader in `vendor/`, which is not under version control.

## Commands

| Command | What it does |
|---|---|
| `./bin/build.php` | Renders the pages for today |
| `./bin/build.php 2027-02-05` | Renders the pages as they will be on the given day, for instance to preview a release. Run `./bin/build.php` again, or `git restore public/`, to get back to today |
| `./vendor/bin/phpunit` | Runs the tests |
| `./tools/phpstan` | Runs the static analysis |
| `./tools/php-cs-fixer fix` | Formats the code |
| `./tools/composer dump-autoload` | Has to be run after a class was added or renamed |

A build stops with a message when the configuration is invalid, when a placeholder of a template is not replaced, or when the logo of a sponsor does not exist. Pages that were rendered before the problem was found are already written at that point, so look at `git status` after a failed build.

## What is where

| Path | Content |
|---|---|
| `config.php` | The single source of truth for versions, release dates, articles, and sponsors. Every key is explained in the comment at the top of the file |
| `templates/pages/` | One template for each generated page |
| `templates/shared/` | The header and the footer, which exist only once |
| `templates/<page>/` | The parts of a page that are repeated, for instance a row of a table |
| `src/` | The generator |
| `tests/` | The tests for the generator |
| `tools/` | Composer, PHPStan, and PHP-CS-Fixer |
| `public/` | The document root. `public/*.html` is generated, the rest is maintained by hand |

Never edit a generated page in `public/`: the next build overwrites the change. Edit its template or `config.php` instead, run the build, and review the diff of `public/`.

These parts of `public/` are **not** generated and have to be edited directly:

* `announcements/`, including its `index.html`
* `code-sprints/`
* `manual/`
* `sitemap.xml`, including the `lastmod` of each page
* stylesheets, fonts, and images

## What is derived

The following is not configured. It follows from the dates in `config.php` and the day of the build:

* The **current major version** is the newest one whose `released` date is not in the future
* The **next major version** is the oldest one whose `released` date is in the future
* The **newest minor version** of a major version is its `minorVersion`, or its `nextMinorVersion` from the day that one is released
* **Bugfix Support** for a major version ends on the day the major version after the next one is released. As long as that one is not configured, this is the first Friday of February two years after the release
* The **status** of a major version (Bugfix Support, Life Support, End of Life) follows from these dates and its `endOfLife`

The pages use this as follows:

| Page | What comes from the configuration |
|---|---|
| `index.html` | Current major version, next minor and next major version with their milestones, the three newest major versions that have an announcement, the three newest articles |
| `supported-versions.html` | The table and the note about the next major version |
| `documentation.html` | The links to the documentation of supported versions and the URLs for unsupported ones |
| `backward-compatibility.html` | The links to `DEPRECATIONS.md` |
| `getting-started.html` | Name of the current major version, name of its PHAR, version constraint for Composer, versions of PHP, newest minor version in the sample output and in the link to the documentation |
| `verify.html` | Name of the current major version and of its PHAR |
| `sponsors.html` | The sponsors |

## A new minor version

Example: PHPUnit 13.5 is released on December 4, 2026.

**Before the release**, at any time, configure it as the next minor version of its major version in `config.php`:

```php
'minorVersion'     => '13.4',
'nextMinorVersion' => [
    'version'   => '13.5',
    'released'  => '2026-12-04',
    'milestone' => 74,
],
```

From the next build on, the homepage says that PHPUnit 13.5 will be the next minor version.

**On the day of the release**, after the release is done:

1. Make sure that what the pages will link to exists: the documentation at `https://docs.phpunit.de/en/13.5/` and `DEPRECATIONS.md` on the `13.5` branch
2. Add the release to `public/announcements/index.html` by hand
3. Run `./bin/build.php`, review `git diff public/`, commit, and push `public/` to the web server

The build replaces 13.4 with 13.5 in the table of supported versions, in the link to the documentation, in the link to `DEPRECATIONS.md`, and in the tutorial. The sentence about the next minor version disappears from the homepage.

**Afterwards**, when it suits:

* Make the released version the `minorVersion` and configure the minor version that follows it as `nextMinorVersion`. Remove `nextMinorVersion` when no further minor version of that major version is planned
* Add the article about the release to `articles`
* Update the `lastmod` of the changed pages in `public/sitemap.xml`

## A new major version

Example: PHPUnit 14 is released on February 5, 2027.

**Before the release**, as soon as the date and the milestone are known, add the major version to `majorVersions` in `config.php`:

```php
[
    'version'             => 14,
    'released'            => '2027-02-05',
    'minimumPhpVersion'   => '8.5',
    'minorVersion'        => '14.0',
    'milestone'           => 75,
    'endOfLife'           => null,
    'deprecations'        => true,
    'tutorialPhpVersions' => ['8.5'],
],
```

From the next build on, the homepage says that PHPUnit 14 will be the next major version, and the page about supported versions says when it is planned and which major version loses its Bugfix Support on that day. `milestone` is required for as long as the version is not released. `tutorialPhpVersions` is required from the day it is the current major version.

**On the day of the release**, after the release is done:

1. Write the announcement, `public/announcements/phpunit-14.html`, and add it to `public/announcements/index.html` and to `public/sitemap.xml`, all by hand. Without this page, the homepage and the table of supported versions name PHPUnit 14 without a link, and the homepage does not list its release
2. Make sure that what the pages will link to exists: `https://phar.phpunit.de/phpunit-14.phar`, the documentation at `https://docs.phpunit.de/en/14.0/`, and `DEPRECATIONS.md` on the `14.0` branch
3. Run `./bin/build.php`, review `git diff public/`, commit, and push `public/` to the web server

The build makes PHPUnit 14 the current major version: on the homepage, including its structured data, in the tutorial, and as the example of the page about verifying releases. It adds PHPUnit 14 to the table of supported versions, to the documentation, and to the lists of deprecations. PHPUnit 12 moves from Bugfix Support to Life Support.

**Review with particular care**, because these are not derived:

* `templates/pages/verify.html` shows captured output for one specific release (`phpunit-13.4.1.phar`). It no longer matches the example once `phpunit-14.phar` is the current PHAR and should be captured again
* `templates/pages/getting-started.html` shows sample output of the test runner. Only the version number in it is derived, so check that it still looks like the output of the new major version
* Texts in templates that name a major version literally, for instance "PHPUnit 14 and newer" on the page about backward compatibility

**Afterwards**, when it suits:

* Configure `nextMinorVersion` for the first minor version of the new major version
* Add the major version after it as soon as its date and milestone are known
* Remove `nextMinorVersion` from the previous major version and set its `minorVersion` to its last minor version
* Add the article about the release to `articles`

When Life Support for a major version ends, set its `endOfLife` and `maximumPhpVersion`. The build then moves it to the older versions of the table and to the unsupported versions of the documentation.

## Other changes

* **A new article:** add it to `articles` in `config.php`. The homepage shows the three newest ones that are published on the day of the build
* **A new sponsor:** put the logo into `public/img/sponsors/` and add the sponsor to `sponsors` in `config.php`
* **A change to the navigation or the footer:** edit `templates/shared/`. The pages below `announcements/` and `code-sprints/` carry their own copy and have to be changed by hand
* **A new top-level page without configured content:** create `templates/pages/<name>.html` with `{{header}}` and `{{footer}}` and add its name to `StaticPageRenderer::PAGES`

## Templates

A template is HTML with `{{placeholders}}`.

A placeholder that stands alone on a line is replaced together with its line: the value brings its own line break, and an empty value leaves nothing behind. Every other placeholder is replaced where it stands.

A page gets the header and the footer through `{{header}}` and `{{footer}}`. The entry of the navigation that links to the page is marked as the current one.

The build fails when a renderer passes a value for a placeholder that the template does not have, and when a placeholder is left over.
